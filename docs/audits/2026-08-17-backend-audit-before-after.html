Three findings that didn't survive verification

The audit was a static sweep, and said so. Checking each finding against the code first — rather than fixing straight from the report — is what surfaced these.

3.3 — “rel_listings / rel_projects / rel_deals have RLS enabled but no policies”

False positive. Those tables do have policies. They are created in migration 20260504141024 inside a DO $$ … EXECUTE format(…) $$ loop over an array of twelve table names — so a grep for CREATE POLICY … ON public.rel_listings finds nothing, which is exactly what the audit's sweep did. Each table gets a rel_auth_read_* SELECT policy and a rel_owner_write_* policy gated by rel_is_owner(). No change was needed; the verification query is recorded in the new migration so the next reader doesn't repeat the finding.

3.2 — “user_sessions still has an unrestricted UPDATE policy”

Already fixed, months before the audit. Migration 20260706161023 replaced USING (true) with USING (user_id = auth.uid()) WITH CHECK (user_id = auth.uid()) on 6 July. The audit read the original January migration and not the July correction. The policy is re-asserted idempotently in the new migration anyway — a later migration touched the INSERT policy on the same table without touching UPDATE, and that is the shape of a silent regression.

4.3 / 4.4 — rate limiting and validation on public endpoints

Partially stale. newsletter-subscribe was named as having “one validation hit total”; it in fact runs the shared rate limiter, a honeypot, an email-format check, a per-email hourly cap, and returns a deliberately uniform response to prevent subscriber enumeration. capture-lead likewise already had DB-backed per-IP rate limiting. The genuine gaps — register-user and booking-public-create — were real, and are fixed.

What is not fixed

Stated plainly, because a remediation report that only lists wins is not useful.

Nothing here is verified live

This is a code-only change, pushed to a branch. No Lovable publish was performed, so none of it is running on jbj.ae yet. Every “fixed” claim on this page means fixed in code and passing tests — not confirmed against the deployed system. The create-checkout fix in particular deserves a live check before it is called done.

Deleting a function does not undeploy it

The four smoke-test endpoints and bulk-import-devs-2027-6 were removed from the repo, but a repo deletion does not remove an already-deployed function from the Supabase project. Until they are explicitly undeployed they remain publicly callable — and bulk-import-devs-2027-6 is not just dead code, it performs unauthenticated service-role writes into the developers table. Tracked as JBJ-027; this one needs action outside git.

The wide sweeps are still wide

225 functions using service-role without a visible caller check, 357 with wildcard CORS, and ~210 with no traceable caller are rollout-scale items, not single fixes. The public-facing subset that mattered most was addressed; the long tail is tracked as JBJ-028 and needs a per-function pass, not a sweep.

A bug the tests caught

The first version of the Sentry PII scrubber silently failed on Full_Name: the key normaliser stripped underscores from the pattern but not from the key, so full_name never matched fullname. Eight unit tests were written alongside it, and one of them caught this. Worth noting because the fix would have looked correct in review.

Verification performed

  • Full Vitest suite: 425 tests across 40 files, all passing — including 8 new tests for the Sentry PII scrubber.
  • tsc --noEmit: no errors in any file this change touches. The suite does report pre-existing errors from a zod v3→v4 API drift, all in files untouched here; confirmed by intersecting the changed-file list against the error list.
  • Pre-commit gates: the repo's static a11y check and low-opacity-contrast checks both ran and passed on the staged diff.
  • Not run: no Deno typecheck of the edge functions — Deno is not installed in this environment, so the 13 changed function files were verified by reading, not by compiler.
